# How LDTD is built

LDTD is a Forge 1.12.2 mod, written in Java 8, under the package
`com.micatechnologies.minecraft.ldtd`.

## Five rules

These hold everywhere in the code base. A change that breaks one is a bug.

1. **Common code never reaches client-only classes.** Renderers, the HUD and the ghost preview
   are only reached through `LdtdClientProxy`. A stray `net.minecraft.client` import in common code
   compiles fine and then crashes a dedicated server. CI's server smoke test catches it.
2. **The server is authoritative.** Hearths, raids, routing, targeting and the builders all run on
   the server. The client only draws.
3. **Simulation cores stay Minecraft-free.** Raid budgets, routing over an abstract grid and the
   balance maths live in `ldtd.sim`, which never imports a `net.minecraft` or
   `net.minecraftforge` type. That keeps them unit-testable on a plain JVM. Convert at the
   boundary.
4. **Content is data.** Towers, Gloam, raids, levels and blueprints are JSON. No balance numbers
   in Java. A broken file never takes a server down.
5. **The Gloam only damage blocks inside a Hearth's territory.** Every block-damage path goes
   through the territory check.

## Packages

| Package | What's in it |
| --- | --- |
| `ldtd` | Mod entry point, config (`LdtdConfig`), registry, constants, proxies |
| `ldtd.hearth` | The Hearth block and tile entity, stockpile, `HearthRegistry`, territory protection, Hearth-sprites and their `BuildQueue` |
| `ldtd.tower` | Tower core, blueprint item and placer, tower tile entity, projectiles, Ember Guards and the Command Brand |
| `ldtd.gloam` | The six Gloam units, their shared base, and `GloamMarch` (route following and digging) |
| `ldtd.raid` | `RaidDirector` (when raids start) and `Raid` (one raid's waves, Flame and ending) |
| `ldtd.route` | The world side of routing: terrain adapter, route cache, siege damage |
| `ldtd.spire` | Dusk Spire worldgen, building, guards and razing |
| `ldtd.village` | The Hearth Square and Watch Post village pieces |
| `ldtd.data` | `LdtdData` (loading, validation, reload) and `JsonMerge` (bringing old files up to date) |
| `ldtd.command` | `/ldtd`, `/hearth` and `/randomspawn` |
| `ldtd.guide` | *The Hearthkeeper's Guide* |
| `ldtd.network` | Client sync |
| `ldtd.client` | Rendering: models, the Gloam renderer, ghost previews, territory borders, health bars |
| `ldtd.sim` | Minecraft-free cores: territory maths, Hearth level table, raid rules and composer, the router, blueprints, tower stats, the balance simulator |

## How a raid flows

```mermaid
sequenceDiagram
    participant D as RaidDirector
    participant H as Hearth
    participant R as Raid
    participant C as RaidComposer (sim)
    participant G as Gloam
    participant RS as RouteService
    D->>H: every second: night? lit? owner near? not raided tonight?
    D->>C: budget + spires → waves of units
    D->>R: start (directions from the nearest spire)
    R-->>R: announce, 30 s countdown
    loop each wave
        R->>G: spawn at the territory edge
        G->>RS: route to the Hearth (shared, cached)
        G->>G: march; dig breaches inside the territory
    end
    G->>H: stand at the Hearth, drain Flame
    R->>H: held / dawn → payout; fell → Hearth goes cold
```

## Names and art

Every name comes from the [naming glossary](../GLOSSARY.md), clash-checked before use. The look
comes from the [art direction](../design/ART_DIRECTION.md): warm (ember, brass) for the Hearth's
side, cold (ink, violet, cyan) for the Gloam. Textures are generated by scripts in `tools/` so
they can be reproduced and reviewed.
